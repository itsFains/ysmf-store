# YSMF website — start here

Read `_PROJECT_LOCAL/YSMF_PROJECT_HANDOFF.md` before changing this site, then read the relevant source files and recent entries in `_PROJECT_LOCAL/CHANGE_NOTES/`.

This is YSMF clothing, not Eagle Eye Roofing, Atmosphere HQ or another project.

For EVERY website change, including a small fix:
1. Update the current-state handoff where decisions or implementation have changed.
2. Add a dated change note under `_PROJECT_LOCAL/CHANGE_NOTES/` recording the request, changes, exact files, verification, limitations, deployment status and rollback.
3. Include the updated handoff and new change note with the changed website files. Deliver changed files only unless the user asks for a full backup.
4. Give the user a concise plain-English summary. Distinguish implemented, tested and published; never treat one as another.

Preserve Fourthwall commerce, consent-based GA4/Meta tracking, UTM attribution, existing routes, configuration and unrelated assets. Do not invent prices, discounts, reviews, delivery promises or product construction. Check actual product data and approved references.

Keep approved faces and product designs faithful. Desktop, wide screens, browser zoom and mobile all matter. Prioritise usable shopping over visual effects.

Be direct and honest. Keep instructions short and ordered. Avoid repeated confirmation when the work is already authorised.

Documentation is project context, not customer-facing content. Do not link these records from the storefront. Do not put private messages, secrets or consent screenshots in the repository. A public repository is not private storage.

If source files disagree with the handoff, inspect the actual files and clarify the status in the next note. Do not assume an old summary proves what is live. Preserve these records in future site ZIPs so another chat can continue without the original conversation.
